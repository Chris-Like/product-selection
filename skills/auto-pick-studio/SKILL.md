# 选品台（auto-pick-studio）

这是 Codex 与 WorkBuddy 共用的选品对话插件。**找机会、验证方向、跟踪候选的问答只在当前宿主对话中完成**；本机页面仅用于站点授权、任务状态、已确认计划、采集和结果。启动后页面在 `http://127.0.0.1:17860/`，所有数据只留本机。

## 示例 prompt

- 「启动选品台」→ 运行 `scripts/start.mjs`，回报本机页面地址。
- 「采一次」→ 运行 `scripts/capture.mjs`，触发一轮串行采集并回报逐站状态。
- 「看下采集状态 / 结果」→ 运行 `scripts/status.mjs`，回报任务态与逐站状态；需要明细时提示用户打开页面「工作台」tab 的结果区（默认本轮，可切全部累计）。
- 「帮我找选品机会 / 验证一个方向 / 跟踪候选」→ 按下方“对话工作流”在当前对话中引导，**不要要求用户回网页填写问卷**。

## 使用约定

- 服务只绑 `127.0.0.1`，端口为示例值，待确认，可用 `AUTO_PICK_PORT` 覆盖。
- 页面按钮与 Skill 脚本共用同一个任务入口（`app/server/task.js` 的 `submit()`），不要另写第二套调度。
- 采集需要 Playwright；未安装时脚本会返回明确提示，不要静默跳过或反复重试。
- 首次或登录态过期时，提示用户在「配置」tab 点该站的「登录」，本人在打开的有头浏览器里手动输入或扫码；系统只保存 `storageState` cookies，**不录入、不保存密码，不自动绕过验证码 / 滑块 / 二次验证**。
- 站点规则 `app/config/site-rules/*.json` 的选择器为空槽时，采集走降级态、不落库；由 B0 真实页面实测回填，**不得猜测或编造选择器**。
- 选品结论由用户本人判断；工具不生成综合分、不输出销量预测。领先标的是经验信号，不是预测结论。
- **必须先确认模式**：若 `guide.mjs start ...` 返回“未启用 Agent 协作”，让用户在选品台「配置」中选择“Agent 协作”；不要替用户改配置。

## 对话工作流（Codex / WorkBuddy）

用户明确要求使用 FastMoss、LinkFox 或调研跨境市场时，先读 [外部数据工作流](references/provider-research.md)。跨境查询使用已授权的宿主工具。缺少工具时给出对应宿主的接入说明。

1. 若服务未启动，运行 `scripts/start.mjs`；若用户尚未选择 Agent 协作，提示其在网页配置后继续。
2. **由插件自动分类，不能把任务类型问题抛给用户**：没有明确方向、询问机会或说“还没想好”用 `opportunity_discovery`；已有商品、场景、类目或风格需要核验用 `direction_validation`；要求复看、比较上次候选或查看变化用 `candidate_follow_up`。仅当三者都无法判断时才问一个自然语言澄清问题。随后运行 `node scripts/guide.mjs start <taskType>`，记录返回的 `session_id` 和 `version`。
3. 用一句话复述目标，主动给出一到两个可查的方向。已知信息足以拟定计划时直接写草案。只有答案会改变检索范围时才问一个问题，并给可直接选用的答案。用 `node scripts/guide.mjs question <sessionId> <version> <field> "问题" "原因"` 写回，再等待回答。
4. 用户回答后，运行 `node scripts/guide.mjs answer <sessionId> <version> "回答"`。基于返回的新版本，继续问一个问题，或形成草案。
5. 整理成一两句可供用户核对的需求摘要。用 `node scripts/guide.mjs stage <sessionId> <version> "搜索词1|搜索词2" "关注点" "反例检查" "预算上限" "需求摘要"` 准备需求卡，没有预算时金额传空字符串。先在对话中展示需求摘要，提供 `assistant_url` 作为「打开需求卡」链接。用户也可留在对话中回复「生成搜索词」或提出修改。修改需求后用当前版本重新 `stage`。
   用户回复「生成搜索词」时，先用 `session <sessionId>` 读取当前步骤。需求待预览时调用 `preview <sessionId> <version>`（已预览时直接读取结果）。给出可修改的搜索词、查找范围、关注点与未知内容，再邀请用户说「开始采集」。网页按钮预览宿主已准备好的建议。
   展示计划时可以先用 `node scripts/guide.mjs readiness` 检查是否可开始。返回 `setup_url` 时，只说明当前需要的操作，并给出对应设置链接。完成设置后沿用这份草案。
   用户明确给出预算上限时，说明预算用于采后统计，保留所有原始观察。
6. 用户明确同意采集后，运行 `node scripts/guide.mjs confirm-and-capture <sessionId> <version>`，使用同一份已展示草案确认并执行一轮。若只同意保存计划，使用 `confirm`。一旦发出采集请求，等待本轮结果。
7. 在原对话中按本轮返回的记录说明查到了什么、什么仍然缺证据、下一步怎么验证，并链接 `results_url`。只引用实际完成的查询与可核对的事实。采集失败或没有有效样本时说明原因和下一步，遇到授权问题再引导打开专业工作台配置。
   若执行返回 `setup`，本轮还未开始，草案保持原样。请用户按链接完成设置后说「继续」，然后沿用本次明确授权提交同一份草案。部分完成时同时说明已有观察和未完成的查询。没有有效样本时，不给商品判断。
   用 `facts.queries` 对照各检索方向，用 `facts.budget` 说明预算内、超预算、缺价格分别有多少条。保留「页面展示价」和「观察条数」的口径。同一商品可能出现在多条查询里，不能用观察条数代替独立商品数。
   若用户从网页开始采集，回到对话后通过 `session <sessionId>` 读取本轮进度和事实，使用已存在的结果。

`next` 用于领取遗留的待处理任务；`session <sessionId>` 用于在丢失上下文后读取任务状态。宿主自行根据回答组织下一问与草案，必须标明未知项、采集范围和反例，不把探索性判断说成市场事实。
